Nineteen eighty-five. Gul Agha publishes a doctoral thesis at MIT that formally defines a model of concurrent computation in distributed systems. Not a product. Not a startup. A mathematical framework. And forty years later, we're still arguing about whether anyone should actually use it.

Let me make the case against it. The Actor model is seductive in the way that pure mathematical abstractions always are. Every entity is an actor. Every interaction is a message. No shared state, no locks, no race conditions. On a whiteboard, it's pristine. In a doctoral thesis, it's elegant. In production, at three AM, when you're trying to trace why actor number forty-seven thousand stopped processing messages and the entire system is backed up because nobody designed for that particular failure mode — it's something else entirely.

One commenter captures this perfectly. They were brought in specifically to help migrate away from an actor-based system. The seduction wore off. The consultants arrived.

And yet.

Look at what survived. Erlang's OTP, which runs most of the world's telephone switching infrastructure and has for decades. Microsoft Orleans. The Pony language, which took Agha's model and asked, what if we designed a type system that makes data races a compile-time error? That's not retreading old ground. That's extending the formal model with capabilities Agha couldn't have anticipated in nineteen eighty-five because the type theory didn't exist yet.

What Agha actually did — and this is what makes the thesis worth reading, not skimming, reading — is define the operational semantics of concurrent computation in a way that's composable. Each actor encapsulates its own state. Communication is asynchronous. The model handles distribution as a first-class concern, not an afterthought bolted onto a sequential paradigm.

That last part matters. Most concurrency models start with sequential computation and try to add parallelism. Agha started with parallelism and showed how sequential behavior emerges as a special case. The inversion is fundamental. It's the difference between adding wheels to a boat and designing something that moves on both water and land from the beginning.

The thesis is a PDF from DTIC, the Defense Technical Information Center. Public research, publicly funded, publicly available. Forty years later, every major cloud platform's distributed computing framework owes a debt to this work. The math is free. The implementations built on it generate billions in revenue. That's the compounding effect of published knowledge — the return extends far beyond any single investor's timeline.

When does a language need types, and when does it need contracts?

It's a question worth sitting with, because the answer reveals something about how we think about correctness itself. Static types catch errors before execution. Contracts catch them at the boundary between trust and the unknown. They operate in fundamentally different problem spaces, and conflating them is how you end up disappointed by both.

This library brings contract-style validation to Nix. The mechanism is almost disappointingly simple. A type is a function that takes data and returns a boolean. That's it. You wrap your validators in a declare call that adds a name and some tracing infrastructure, compose them with combinators like not and enum and listOf, and then you apply them at the points where untrusted data enters your system. The package dot json example in the article is the right instinct — you're not typing your entire Nix expression, you're validating the boundary where external JSON meets your derivation logic.

The Nix community comment split is instructive. One response calls runtime assertions a poor substitute for a type system. And that's technically correct — but it misses the point. Nobody is proposing this as a replacement for Dhall or Nickel. Those languages were designed from scratch with type systems. Nix wasn't. Nix has millions of lines of existing code in nixpkgs, and nobody is rewriting that corpus in a different language. The question isn't whether static types are superior in the abstract. The question is what you can retrofit onto a running system without stopping the world.

This is where contracts earn their place. They're defensive engineering at system boundaries. You don't need to type every internal function if you can guarantee that data entering your system conforms to a known shape. It's the same principle behind input validation in any security-conscious codebase. Trust the interior, verify the perimeter. The library is open source, composable, and compatible with the existing Nix ecosystem. No revolution required. Just a checkpoint where you need one.

Backups. Specifically, the kind you build yourself with rsync because you looked at Time Machine and thought, I know what's actually happening here.

---

Hard links. That's the primitive. Not snapshots, not deduplication, not content-addressable storage. Hard links. A filesystem feature that predates most of the people reading this article, and it solves the backup versioning problem with zero additional software, zero daemons, zero configuration files.

Let me describe what rsync's link-dest flag actually does, because it's worth understanding the mechanics. When you create a new backup snapshot, rsync compares the source against a reference directory. For every file that hasn't changed, it doesn't copy anything. It creates a hard link, a second directory entry pointing to the same inode on disk. The file exists once in storage but appears in every snapshot that contains it. You get the full directory tree for every point in time, browsable with ls and cd, and you pay storage costs only for the deltas.

Run this forward. What's the failure mode? Hard links operate within a single filesystem. No cross-device linking. No checksumming against bit rot. No encryption at rest. If the underlying block device fails, every snapshot pointing to that inode fails simultaneously. The redundancy is logical, not physical. You still need an offsite copy, and this script doesn't give you one.

The comments point straight at borg, and they're right to. Borg gives you deduplication, compression, encryption, and integrity verification. It's a proper backup system. But there's a reason this rsync pattern keeps getting rediscovered every few years, going back to Mike Rubel's original writeup in the early two-thousands. It has no dependencies. The restore path is cp. Not a proprietary restore tool, not a daemon that needs to be running, not a binary format that might not be readable in ten years. Just a directory full of files.

That's the tradeoff worth sitting with. Sophistication versus legibility. Every backup system you can't restore from without its own toolchain is a system with a single point of failure that isn't on the architecture diagram.
